# Release Process

> A predictable, repeatable release lifecycle for HR Skills packages,
> generated artifacts, and GitHub distribution.

## What it is

This document is the authoritative reference for how HR Skills goes from a
merged change on `dev` to a versioned release on `main`. It covers Changesets,
validation, generated artifacts, tagging, GitHub Release creation, and
rollback guidance.

It complements, and does not replace:

- [`.changeset/README.md`](../../.changeset/README.md) — contributor-facing
  Changesets guidance
- [`docs/engineering/registry.md`](../engineering/registry.md) — registry
  schema and generated-artifact freshness rules
- [`docs/integrations/README.md`](../integrations/README.md) — supported
  distribution surfaces
- [`AGENTS.md`](../../AGENTS.md) — branch strategy and repository workflow

## Current package model

The repository is a Bun/Turborepo monorepo. The root `package.json` is the
private workspace root (`hr-skills-monorepo`, currently `1.4.0`); it is not the
release package.

| Package | Current state | Release role |
| --- | --- | --- |
| `packages/hr-skills` | `0.0.0`, public package, CLI `hr-skills` | Publishable CLI package and primary distribution package |
| `packages/hr-skills-build` | `0.0.0`, `private: true` | Internal build, validation, sync, registry, and packaging tooling |
| `packages/hr-skills-ref` | `0.0.0`, not marked private | Public-capable TypeScript reference library; version only when a Changeset requires it |
| `packages/hr-skills-tsdoc` | Workspace tooling | API-documentation generation; not treated as the primary distribution package |

The `.changeset/config.json` uses public access and currently ignores only
`hr-skills-web`. Do not assume the root workspace version, package versions,
or Changesets versions are interchangeable; inspect the package manifests and
pending Changesets before cutting a release.

### Generated package payloads are not source files

`packages/hr-skills/scripts/prepare-package.ts` is responsible for the
publish-time payload of `hr-skills`. It removes and recreates
`packages/hr-skills/skills/` and `packages/hr-skills/registry/` from the
repository's canonical `skills/` and `registry/skills.json` during packaging.
Those package-local directories are therefore generated staging content, not
independent sources of truth.

Do not delete, hand-edit, or "clean up" generated package payloads as part of a
documentation-only release change. The canonical generated artifacts remain
`registry/skills.json`, `docs/engineering/skill-matrix.md`, and
`.claude-plugin/marketplace.json`, each regenerated by its corresponding
repository command.

## Release lifecycle

### 1. Change + Changeset

For a user-facing package or library change, add a Changeset in the same PR:

```bash
bun changeset
```

Select the appropriate bump and describe the externally relevant change.
Changesets should identify the affected package rather than treating the
private workspace root as the release artifact.

### 2. Merge `dev` into `main`

All feature work lands on `dev`. When the development branch is ready to
release, merge it into `main` through a pull request. `main` is the publishing
branch.

### 3. Release automation creates or updates the Version Packages PR

`.github/workflows/release.yml` runs on pushes to `main`. It first runs:

```bash
bun run validate
```

It then invokes `changesets/action@v1.9.0` with `bun run release`, which runs
`changeset version`. The action creates or updates the release PR containing
package version changes and `CHANGELOG.md` updates.

### 4. Review and merge the release PR

Before merging, verify:

- the affected package versions and bump levels match the Changesets
- generated registry/marketplace artifacts are current
- validation, typecheck, tests, lint, and link checks pass in CI
- the changelog entry accurately describes the released changes

Merging the Version Packages PR updates `main`; it does not itself create the
GitHub Release artifacts.

### 5. Tag the released version

The tag should correspond to the package version being released. For the
primary CLI package, inspect:

```bash
node -p "require('./packages/hr-skills/package.json').version"
```

Then, from the up-to-date `main` after the release PR is merged:

```bash
git tag vX.Y.Z
git push --tags
```

Do not invent or reuse a version. Confirm the exact package version first.

### 6. Tag-triggered GitHub Release

`.github/workflows/publish.yml` runs for `v*` tags. It:

1. installs dependencies with Bun
2. runs `bun run validate`
3. runs `bun run build-skills`
4. extracts the matching `CHANGELOG.md` section
5. creates the GitHub Release
6. attaches `dist/hr-skills.zip` and `dist/hr-skills.skill`

The workflow currently creates GitHub Release artifacts; it does **not** run
`npm publish`. Any future npm publication step must be explicitly added to the
release workflow and documented here before being treated as automated.

## Lifecycle at a glance

| Stage | Trigger | Output |
| --- | --- | --- |
| 1. Changeset | User-facing PR | `.changeset/*.md` |
| 2. Merge | `dev` → `main` PR | Release-ready `main` |
| 3. Version PR | Push to `main` | Package version + `CHANGELOG.md` PR |
| 4. Merge version PR | Maintainer approval | Versioned `main` |
| 5. Tag | Maintainer | `vX.Y.Z` git tag |
| 6. Publish workflow | `v*` tag | GitHub Release + `dist/` artifacts |

## Versioning strategy

HR Skills uses Semantic Versioning through Changesets for packages that are
participating in the release.

| Bump | When to use | Examples |
| --- | --- | --- |
| **major** | Breaking change to a consumer-facing package or contract | Removing a public API, changing a registry schema in a breaking way |
| **minor** | Backward-compatible public capability | New CLI capability, new public API, new generated integration |
| **patch** | Backward-compatible correction | Content fixes, prompt/example fixes, validator or documentation fixes |

Repository and artifact versions are separate concerns:

- The root `hr-skills-monorepo` version identifies the private workspace and
  is not the CLI package version.
- A skill's `metadata.version` in `SKILL.md` tracks that skill independently
  from package releases.
- `registry/skills.json` has its own `schemaVersion`; breaking schema changes
  require the corresponding release bump for consumers of that schema.
- Changesets determines package bumps from pending Changesets. Do not manually
  synchronize unrelated package versions just to make numbers match.

## Release validation checklist

### Automated

- [ ] `bun run validate` passes, including generated registry/marketplace
      consistency checks
- [ ] `bun run typecheck` passes
- [ ] `bun run test` passes
- [ ] `bun run lint` and `bun run lint:md` pass
- [ ] `bun run lint:links` passes
- [ ] `bun run knip` passes
- [ ] pending Changesets are reflected in the release PR
- [ ] `publish.yml` validates the exact tagged commit before building release
      artifacts

### Manual

- [ ] The package(s) named by the pending Changesets are the packages actually
      affected by the change
- [ ] The release version does not come from the private root workspace by
      accident
- [ ] `registry/skills.json`, `docs/engineering/skill-matrix.md`, and
      `.claude-plugin/marketplace.json` are current generated outputs
- [ ] No generated package staging directory was manually deleted or edited
- [ ] The matching `CHANGELOG.md` section exists before tagging
- [ ] The tag points at the exact `main` commit containing the merged release
      PR

## Generated artifacts and source of truth

Never hand-edit generated artifacts to force a release to pass.

| Artifact | Source / command |
| --- | --- |
| `registry/skills.json` | `bun run registry` |
| `docs/engineering/skill-matrix.md` | `bun run matrix` |
| `.claude-plugin/marketplace.json` | `bun run sync` |
| `packages/hr-skills/skills/` | Generated by `packages/hr-skills/scripts/prepare-package.ts` during packaging |
| `packages/hr-skills/registry/skills.json` | Generated by `packages/hr-skills/scripts/prepare-package.ts` during packaging |
| `dist/hr-skills.zip` / `dist/hr-skills.skill` | Built by the tagged publish workflow |

If a generated artifact is stale, fix its canonical input and rerun the
corresponding generator. Do not delete the generated file as a shortcut.

## Release notes workflow

Changeset descriptions become release-note material through Changesets and
`CHANGELOG.md`.

Write each description as a complete statement that identifies the affected
package, skill, command, or public behavior. For bulk skill changes, state the
resulting state or count when that count is intentionally part of the release
record.

Historical `CHANGELOG.md` entries are immutable release history. Do not
rewrite released sections to correct a current documentation issue; correct
future behavior in a new release instead.

## Responsibilities

| Role | Responsibility |
| --- | --- |
| Contributor | Add an accurate Changeset when the change requires one |
| Reviewer | Verify package scope, bump type, generated artifacts, and release notes |
| Maintainer | Merge the release PR, verify the tag, and monitor the publish workflow |

## Rollback guidance

Releases are append-only. Do not reuse or force-move a released version.

### A problem is found after tagging

1. Fix the issue on `dev` as a normal change.
2. Add the appropriate Changeset.
3. Release a new version through the normal lifecycle.
4. Keep the original tag and GitHub Release as historical records.

### A tag was pushed to the wrong commit before external distribution

If the error is caught immediately and the tag has not been consumed or
announced externally, correct the tag only after confirming the intended commit
and version. Otherwise, ship a new corrective version rather than rewriting
release history.
