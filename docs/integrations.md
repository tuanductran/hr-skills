# Ecosystem Integrations

> Phase 5 of the [roadmap](ROADMAP.md) — extending HR Skills interoperability
> across AI agent platforms and marketplaces.

## What it is

HR Skills is authored once, against the open **Agent Skills** specification
(`SKILL.md` frontmatter + Markdown), and distributed to multiple consumption
surfaces without forking content per platform. This document is the
authoritative reference for:

- which platforms are supported today, and which are candidates
- how installation and onboarding work on each
- what a new platform integration must satisfy before it is added
- how compatibility is verified and kept from regressing

It complements `docs/registry.md` (machine-readable skill index) and
`docs/format.md` (skill package structure) — those define the artifact,
this defines where the artifact goes.

## Design principle: one format, many consumers

No skill content is ever duplicated or platform-forked. Every integration is
one of two things:

1. **A copy/reference mechanism** — pointing a platform at `skills/hr-*/`
   or `.claude-plugin/marketplace.json` as-is (Claude Code, claude.ai,
   skills.sh, direct clone).
2. **A generated adapter** — a build step that reads `registry/skills.json`
   or `SKILL.md` frontmatter and emits a platform-native manifest, committed
   alongside the generated artifacts the repo already produces
   (`docs/skill-matrix.md`, `.claude-plugin/marketplace.json`).

If a platform requires content to be rewritten by hand to work, it is not
a supported integration target — see
[Platform-specific implementations](#platform-specific-implementations).

## Supported platforms

| Platform | Mechanism | Status | Notes |
| --- | --- | --- | --- |
| Claude Code | Copy `skills/hr-*` into `~/.claude/skills/` | 🟢 Supported | Recommended path; auto-discovery, no manifest needed |
| Claude.ai (Projects) | Upload `SKILL.md` to Project Knowledge | 🟢 Supported | Single-skill or multi-skill upload |
| Claude Code Marketplace | `.claude-plugin/marketplace.json` | 🟢 Supported | Generated by `bun run sync`; installed via `npx skills add tuanductran/hr-skills` |
| skills.sh | `skills.sh/tuanductran/hr-skills` | 🟢 Supported | Reads the same marketplace manifest |
| Direct clone / vendoring | `git clone` + copy `skills/` | 🟢 Supported | No tooling dependency; works with any Agent Skills–compatible runtime |
| Generic Agent Skills runtimes | Read `SKILL.md` frontmatter directly | 🟡 Candidate | Any runtime implementing the open spec; no adapter needed if it parses frontmatter correctly (see [testing strategy](#integration-testing-strategy)) |
| OpenAI-style custom agents / GPTs | Adapter: registry → tool/instruction bundle | 🟡 Candidate | Requires a generated adapter (see below); no committed adapter yet |
| LangChain / CrewAI / other orchestration frameworks | Adapter: registry → tool schema | 🟡 Candidate | `registry/skills.json` already contains the structured fields (`capabilities`, `triggerPhrases`, `domain`) an adapter would need |

🟢 Supported = works today with no repository changes.
🟡 Candidate = compatible with the architecture, no generated adapter exists
yet. Adding one is a Phase 5 task, not a redesign.

## Installation & onboarding

### Claude Code (recommended)

```bash
# Single skill
cp -r skills/hr-recruiting ~/.claude/skills/

# Full library
cp -r skills/hr-* ~/.claude/skills/
```

### Claude Code Marketplace / skills.sh

```bash
npx skills add tuanductran/hr-skills
```

Both read `.claude-plugin/marketplace.json`, which is generated — never
hand-edited — by `bun run sync` from skill frontmatter. No separate
onboarding path is maintained for these two; they are the same manifest.

### Claude.ai

1. Create or open a Project.
2. Upload the desired `SKILL.md` file (and, for richer skills, the
   `content/`, `prompts/`, `examples/` files) to Project Knowledge.
3. Start chatting.

### Direct clone (any Agent Skills–compatible runtime)

```bash
git clone https://github.com/tuanductran/hr-skills.git
```

Point the runtime's skill loader at `skills/hr-*/SKILL.md`. Because
frontmatter is spec-compliant YAML with only `name`, `description`, and
`metadata`, any runtime that implements the Agent Skills spec can parse it
without repository-specific code.

### Onboarding quality bar

Every supported platform must satisfy all of the following before it is
listed as 🟢 Supported in the table above:

- Installable in **3 steps or fewer** from a clean environment.
- No manual editing of `SKILL.md` or skill directory contents required.
- Documented in this file with a copy-pasteable command or step list.
- Covered by at least one check in [Integration testing strategy](#integration-testing-strategy).

## Adding a new platform integration

1. **Evaluate compatibility first.** Confirm the platform can either (a)
   read `SKILL.md` frontmatter directly, or (b) consume a generated
   manifest derived from `registry/skills.json`. If neither is possible
   without forking skill content, do not add the integration — see
   [Platform-specific implementations](#platform-specific-implementations).
2. **Prefer generation over authoring.** If the platform needs a manifest
   HR Skills doesn't already produce, add a generator under
   `packages/hr-skills-build/src/` that derives it from
   `buildRegistry()` — the same pattern used for
   `.claude-plugin/marketplace.json` and `docs/skill-matrix.md` — rather
   than hand-writing platform-specific files.
3. **Wire it into the existing pipeline**, not a parallel one:
   - a `bun run <name>` script in the new package and root `package.json`
   - a `turbo.jsonc` task with the correct `outputs`
   - a `validateRegistryConsistency()`-style check in `validate.ts` so a
     stale or inconsistent generated manifest fails CI, the same way a
     stale `marketplace.json` or `registry/skills.json` does today
4. **Document it in this file**: add a row to
   [Supported platforms](#supported-platforms), an install snippet under
   [Installation & onboarding](#installation--onboarding), and any
   [platform limitation](#platform-limitations) discovered while building
   the adapter.
5. **Add an integration test** per the strategy below before marking the
   platform 🟢 Supported.

## Integration testing strategy

Compatibility is verified at three layers, mirroring the existing
validation layers described in `docs/ROADMAP.md`:

1. **Format-level (spec compliance).** `bun run validate` already asserts
   every `SKILL.md` has valid frontmatter, required fields, and a directory
   name matching `name`. This is the baseline every platform integration
   relies on — if it passes, any spec-compliant runtime can load the skill.
2. **Manifest-level (generated artifact freshness).** For every generated
   adapter (`marketplace.json`, `registry/skills.json`, and any future
   platform manifest), a consistency check recomputes the manifest in
   memory and diffs it against the committed file, the same pattern as
   `validateRegistryConsistency()`. A stale manifest fails CI before it
   reaches a platform.
3. **Platform-level (smoke test).** For each 🟢 Supported platform, a
   minimal, manual or scripted smoke test confirms:
   - the install steps in this document complete without error
   - at least one skill loads and its `description` triggers correctly
   - no skill content is altered in transit (diff the loaded skill against
     the source `SKILL.md`)

   Platform-level tests are tracked as GitHub issues per platform rather
   than committed CI jobs where the platform has no scriptable API
   (e.g. claude.ai Project Knowledge upload). Where a platform does expose
   a CLI or API (Claude Code, skills.sh), the smoke test should be
   automated in CI as it is added.

A platform only moves from 🟡 Candidate to 🟢 Supported once all three
layers pass.

## Backward compatibility

- Existing integrations (Claude Code, claude.ai, marketplace.json,
  skills.sh, direct clone) are never modified by adding a new platform
  integration — new adapters are additive generation steps, not changes to
  `SKILL.md` or existing manifests.
- `registry/skills.json` and `.claude-plugin/marketplace.json` schema
  changes follow the existing versioning rule in `docs/registry.md`
  (bump `schemaVersion` / regenerate + validate) — a new platform adapter
  must not force a breaking change to either.
- Any platform-specific quirk that requires workaround content (e.g. a
  platform that truncates descriptions, or enforces a stricter
  frontmatter schema) is documented under
  [Platform limitations](#platform-limitations) instead of being solved by
  altering the shared `SKILL.md`.

## Platform limitations

Known constraints discovered while integrating, kept up to date as new
platforms are added:

- **claude.ai Project Knowledge** has a per-project file/character budget;
  very large multi-skill uploads (e.g. `skills/hr-*` in bulk) may need to
  be split across Projects. There is no manifest for this platform because
  the upload path is manual by design.
- **Generic Agent Skills runtimes** vary in how strictly they validate
  frontmatter. HR Skills targets the published spec exactly (`name`,
  `description`, `metadata.author`, `metadata.version`) and adds nothing
  proprietary, so any spec deviation is a bug in the runtime, not a reason
  to add runtime-specific fields to `SKILL.md`.

## Platform-specific implementations

HR Skills deliberately avoids integrations that require:

- forking or rewriting `SKILL.md` content per platform
- adding platform-only frontmatter fields consumed by a single runtime
- maintaining a second, hand-edited copy of any generated manifest

If a platform cannot be supported without one of the above, it stays out of
[Supported platforms](#supported-platforms) until an open-standard adapter
path exists (open format extension, plugin spec, or community-maintained
converter), consistent with the "prefer open standards and reusable
integration patterns" principle this document follows.
