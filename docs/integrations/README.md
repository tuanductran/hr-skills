# Ecosystem Integrations

> How HR Skills extends interoperability across AI agent platforms and marketplaces.

This document is authoritative for which platforms are supported today, which are candidates, how installation works, and how compatibility is verified.

## Design principle: one format, many consumers

No skill content is duplicated or platform-forked. Every integration is one of:

1. A copy/reference mechanism pointing a platform at canonical `skills/hr-*/` content or a generated marketplace manifest.
2. A generated adapter/manifest derived from canonical skill metadata.

If a platform requires hand-written forks of skill content, it is not a supported integration target.

## Supported platforms

| Platform | Mechanism | Status | Notes |
| --- | --- | --- | --- |
| Claude Code | Copy `skills/hr-*` into `~/.claude/skills/` | 🟢 Supported | Documented consumption path; canonical skill structure is validated in repository CI |
| Claude.ai (Projects) | Upload `SKILL.md` to Project Knowledge | 🟢 Supported | Documented consumption path; third-party runtime behavior is outside repository CI |
| Claude Code Marketplace | `.claude-plugin/marketplace.json` | 🟢 Supported | Generated by `bun run sync` and validated in repository CI |
| Direct clone / vendoring | `git clone` + copy `skills/` | 🟢 Supported | No tooling dependency; targets Agent Skills-compatible runtimes |
| Codex plugin manifest | `.codex-plugin/plugin.json` | 🟡 Manifest generated | Generated and schema-validated; runtime compatibility is not claimed solely because the manifest exists |
| Codex plugin marketplace manifest | `.agents/plugins/marketplace.json` | 🟡 Manifest generated | Generated and schema-validated; marketplace availability remains platform-dependent |
| Generic Agent Skills runtimes | Read `SKILL.md` frontmatter directly | 🟡 Candidate | Compatibility depends on the runtime implementing the open specification |
| OpenAI-style custom agents / GPTs | Adapter: registry → tool/instruction bundle | 🟡 Candidate | No dedicated generated adapter is committed |
| LangChain / CrewAI / other orchestration frameworks | Adapter: registry → tool schema | 🟡 Candidate | Registry contains structured fields an adapter could use |

🟢 Supported means the documented consumption path and repository-controlled
artifacts are implemented and verified. It does **not** mean the third-party
runtime itself is executed in CI. Platform-specific runtime behavior remains
outside repository verification unless a dedicated external-platform harness is
actually maintained.

## Installation & onboarding

### Claude Code

```bash
cp -r skills/hr-recruiting ~/.claude/skills/
cp -r skills/hr-* ~/.claude/skills/
```

### Claude.ai

1. Create or open a Project.
2. Upload the desired `SKILL.md` and, where useful, its `content/`, `prompts/`, and `examples/` files.
3. Start chatting.

### Direct clone

```bash
git clone https://github.com/tuanductran/hr-skills.git
```

Point the runtime's skill loader at `skills/hr-*/SKILL.md`.

## Generated integration artifacts

`bun run sync` keeps these committed manifests aligned with canonical skill and
package metadata:

- `.claude-plugin/marketplace.json`
- `.claude-plugin/plugin.json`
- `.codex-plugin/plugin.json`
- `.agents/plugins/marketplace.json`
- root `SKILL.md` routing table

These are generated artifacts, not independent sources of truth.

## Adding a new platform integration

1. Confirm the platform can read `SKILL.md` directly or consume a generated manifest.
2. Prefer a generator under `packages/hr-skills-build/src/server/build/` over hand-written platform content.
3. Wire the generator into the existing `sync`/validation pipeline.
4. Document the platform and its limitations here.
5. Add an integration test before claiming full support.

## Integration testing strategy

Compatibility is checked at two repository-controlled layers:

1. **Format-level:** `bun run validate` checks skill frontmatter and structure.
2. **Manifest-level:** generated artifacts are regenerated or validated against canonical metadata.

For third-party runtimes such as Claude Code or Claude.ai, repository CI does
not authenticate to or execute the external platform. Therefore this repository
does not claim a platform-level smoke test unless a dedicated test harness is
present and maintained.

A generated manifest alone is not evidence of end-to-end runtime support.

## Backward compatibility

Existing integrations remain based on canonical `SKILL.md` files and registry.
New adapters should be additive and must not require platform-specific forks.

## Platform limitations

- **Claude.ai Project Knowledge** has per-project upload limits; large libraries may need to be split across Projects.
- **Codex manifests** are generated and schema-validated here, but this repository does not claim marketplace/runtime support merely from manifest generation.
- **Generic Agent Skills runtimes** vary in strictness; HR Skills targets the published specification rather than runtime-specific frontmatter.

## Platform-specific implementations

HR Skills deliberately avoids integrations that require:

- forking or rewriting `SKILL.md` content per platform
- platform-only frontmatter fields consumed by a single runtime
- maintaining a second, hand-edited copy of generated manifests
